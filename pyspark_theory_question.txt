 Transformations vs Actions: Transformations are lazy and build a plan, while actions trigger execution.

Transformations (Lazy): These DO NOT execute immediately
A transformation is an operation on a DataFrame/RDD that creates a new dataset from an existing one without executing immediately.
Example : 
select()-select columns
filter()-row filters
withColumn()- create columns
drop()-remove columns
groupBy()-create groups
join()-join datasets
distinct()-unique rows

Just builds a plan
No execution yet 

Actions (Trigger execution): These START execution
An action is an operation that triggers execution of transformations and returns a result (to driver or writes to storage).
Examples:
show()- display data
count()- number of rows
collect()- bring data to driver (DANGEROUS for big data!)
take()- return first N rows
write()- save output
 
Spark actually runs the job


Lazy Evaluation:
Spark does NOT run immediately when you write code like:
df1 = df.filter(df.age > 25)
df2 = df1.select("name")
df3=df2.withcolumn(“capital_name”, upper(col(“name”)))
Nothing runs yet ❌


Spark waits until it hits an ACTION (like show(), count(), collect())
Then Spark runs all previous steps in one optimized way.

 Why lazy evaluation?
Better performance
Optimizes the plan (Catalyst optimizer)
Avoids unnecessary computations

 DAG (Directed Acyclic Graph): Spark builds a DAG (execution plan)
Above example 
filter → select → withColumn → show()

Spark converts this into: Optimized execution plan
When you do many transformations:

Spark stores all steps in a lineage graph.

Spark uses this graph for: 
optimization,

  Repartition vs Coalesce
To control parallelism, performance, and number of output files.
Spark works on partitions. If partitions are not managed properly:
jobs become slow
resources are wasted
too many small files are created
More partitions → more parallelism
Fewer partitions → less overhead

repartition(n)
Increases or decreases number of partitions
Causes a full shuffle
Expensive
Used when you want balanced partitions
example: 
df = df.repartition(10)
 
When to use it :
Before large joins (Joins & groupBy need balanced data.)
Before writing large files
When existing partitions are unbalanced(Some partitions huge, some small → slow job. Repartition redistributes data evenly.)
Example:
Before:
Partition 1 → 100 rows 
Partition 2 → 5 rows 
Partition 3 → 200 rows 
After repartition(2):
Partition 1 → ~150 rows 
Partition 2 → ~155 rows 

Balanced,Expensive (shuffle)


coalesce(n)
Only reduces number of partitions
NO shuffle (faster)
Data is moved minimally
Example :
df = df.coalesce(2) 
When to use :
After filtering data(Data shrinks but partitions remain same → waste resources.  Fewer tasks, Better resource usage)
Before writing a small output
When you want fewer output files
By default: df.write.parquet("output/")
Creates many small files.
df.coalesce(1).write.parquet("output/")- Single output file
Example:
Before:
Partition 1 → 100 rows 
Partition 2 → 5 rows 
Partition 3 → 200 rows 
After coalesce(2):
Partition 1 → 100 rows 
Partition 2 → 205 rows   ❌ (imbalanced)
Fast,Uneven data distribution
 

We use repartition and coalesce to control the number of partitions in Spark, which helps improve parallelism, balance workload, reduce small files, and optimize performance. Repartition performs a full shuffle and is used when increasing or balancing partitions, while coalesce reduces partitions without shuffle and is used after filtering or before writing output.

 What is User Defined Function?
Used when Spark doesn’t have a built-in function we required Complex custom logic.
example:
from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

def category_func(age):
    return "Senior" if age > 28 else "Junior"

udf_func = udf(category_func, StringType())
df.withColumn("category", udf_func("age")).show()

Why UDF is Slow?
UDFs are slow because they involve serialization between JVM and Python and bypass Spark’s Catalyst optimizer.

Spark runs in JVM
Python runs separately
Data moves between JVM ↔ Python (serialization)
Result -Slow performance, Breaks Spark optimization

Better Alternative:
Use inbuilt function: 
from pyspark.sql.functions import when, col
df.withColumn(
"category",
when(col("age") > 28, "Senior").otherwise("Junior")
) 
Faster and Optimized
 
When Built-in Spark functions are not enough:
Then you have 2 options:
Use UDF (slow)
Use Pandas UDF (better)

Instead of using UDF we can  Use Pandas UDF(faster then UDF):
UDF = You process 1 record at a time
Pandas UDF = You process 1000 records together
(Batch processing = faster )

Pandas UDF is used in Spark to efficiently execute custom Python logic in a vectorized manner using Apache Arrow, making it faster than regular UDFs.

Data Skew :
Data Skew occurs when data for certain keys is unevenly distributed, causing some Spark tasks to run much longer than others. It leads to poor parallelism and slow jobs. Common solutions include broadcast joins, salting heavy keys, and repartitioning using high-cardinality columns. 

Data Skew happens when data is not evenly distributed across partitions.
If one task has too much data, That task runs much longer than others,  Entire job waits for that one task.

Example:
80% rows = India, when group by country
One partition gets all India rows, One executor gets overloaded

Symptoms:
One task takes much longer
Spark UI → one task has huge input size
CPU usage uneven
Stage stuck at 99%

SOLUTION:
1. Broadcast Join:
One table is small, Another table is large
Small table goes to all executors
shuffle
No skew

2. Salting Keys:
You artificially split heavy keys into smaller keys.
Like india into India_1, India_2, India_3, India_4
Example:
Add salt
from pyspark.sql.functions import rand, concat, lit
df_salted = df.withColumn(
    "country_salt",
    concat(df.country, lit("_"), (rand()*5).cast("int"))
)
 
Group using salted key:
df_salted.groupBy("country_salt").count() 

3. Repartition by Better Column:
You partition by bad column (low cardinality)
Example in above case instead of using country we can use any other column like used_id

Broadcast Join :
Broadcast join avoids shuffle by sending small data to all executors.

Splits both datasets into partitions
Moves data across network
Matches keys

Very slow
 
 What happen in broadcast join:
 small_df → copied to all executors

Executor 1: large_df_part + small_df
Executor 2: large_df_part + small_df

Each executor joins locally
No shuffle
Much faster

When one dataset is small enough to fit in memory.

 Job,stage task,executor:
Spark executes it in this hierarchy:
Application → Job → Stage → Task
 
 What is an Executor?
A worker process that executes tasks and stores data.
Worker doing actual work

What is a Task? 
Smallest unit of work executed on a partition.
One partition = One task
Operates on one partition
Runs inside an executor

What is a Stage?
Set of tasks executed in parallel between shuffle operations. 
Stage = Group of tasks
Tasks that can run in parallel
Created based on shuffle boundaries
Total stages= no of wide transformation +1

What is a Job? 
Triggered by an action
Each action = 1 job
For example:
df.filter("age > 25").groupBy("city").sum().show()
Action -> show() 1 job 
Stages:
filter() → no shuffle → Stage 1
groupBy() → shuffle → Stage 2 
Tasks:
If each task has 4 partition
 Stage 1 → 4 tasks
Stage 2 → 4 tasks  
Executors:
Executor 1 → Task 1 
Executor 2 → Task 2 
Executor 3 → Task 3 
Executor 4 → Task 4 

Visual flow :
Driver
↓
Job (triggered by action)
↓
Stage 1 (no shuffle)
↓
Tasks (per partition)
↓
Stage 2 (after shuffle)
↓
Tasks
↓
Executors execute tasks 


Complete Flow of execution of pyspark job  (One Line):
Code → Lazy Transformations → Action
→ Logical Plan → Catalyst Optimization
→ Physical Plan → DAG → Stages → Tasks
→ Executors → Result
In PySpark, a query is lazily evaluated. Once an action is called, 
Spark builds a logical plan, 
optimizes it using Catalyst, 
converts it into a physical plan and DAG, 
splits it into stages based on shuffle boundaries, 
executes tasks on executors, 
and finally returns the result to the driver.

Performance Optimization (Production Level):
Partitioning,repartition before write, Broadcast join, Cache
Partitioning improves read performance, repartition controls output data distribution, broadcast join avoids shuffle for small tables, and cache avoids recomputation.

Partitioning
Splitting data into smaller chunks based on a column
Example:
gold/sales/
city=delhi/
city=mumbai/
 
Why we use it?:
Faster queries
Less data scan
Better performance
 
Real Scenario:
Without partition:
Full data scan
With partition:
Only city=Delhi folder read 
 
Repartition before write:
Redistributes data into new partitions (with shuffle) but expensive due to shuffles
Example:
df_gold.repartition(4, "city")
 
Why we use it?
Control number of output files
Avoid too many small files
Better parallelism
 
Real Scenario:
Without Repartition:
1000 small files
S3 performance issue
Time take by Query engines

With Repartition:
4 optimized files 
 
Broadcast Join:
Send small table to all executors to avoid shuffle:
Example:
df_final = df_sales.join(
broadcast(df_products),
"product_id"
) 
 
Why we use it?:
Avoid shuffle
Faster joins
 
Real Scenario:
Table		Size
sales		1GB
products	5MB 
 
Without Broadcast:
Shuffle happens ❌ slow operation
 
With Broadcast:
No shuffle ✅ fast operation 
 
Cache:
Store DataFrame in memory for reuse
Example:
df_final.cache()
 
Why we use it?:
Avoid recomputation
Faster repeated operations
 
Real Scenario:
without cache:
df_final.count()
df_final.show()
👉 Spark recomputes twice
 
With cache:
Compute once → reuse
