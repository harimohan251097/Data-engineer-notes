1. What is PySpark?
PySpark is the Python API for Apache Spark.which is a powerful framework used for big data processing and distributed computing.
Instead of processing data on a single computer, PySpark distributes the work across a cluster (many computers working together).
Works on Driver + Executors architecture
Code → DAG → Tasks → Executed in parallel on cluster
Why PySpark is used? 
Handling big data (GBs to TBs+)
Running computations in parallel
Being faster for large-scale processing
Supporting batch processing + real-time streaming

2. Spark Architecture
Spark follows a Master–Worker architecture designed for distributed data processing.

High-Level Components:
Driver (Master Node) (brain):
Creates SparkSession
Request resource to cluster manager
Builds execution plan (DAG)
Generate logic or physical plan which decide no of job, stage and task
Sends tasks to executors
Collects results

Cluster Manager (resource allocator):
Manages resources (CPU, memory)
Allocates resources to Spark applications
Decide how many executors to launch 
Examples: Yarn (in hadoop)
 
Worker Nodes(worker):
Machines where actual computation happens
Machines on cluster that run executor 
On heap memory(executor) and off heap memory(to keep garbage)
 
Executors(worker doing job):
Transformation and action perform on actual data
Execute task as per physical plan 
Responsibilities:
Execute tasks
Store data in memory/cache
Return results to Driver
 
Job, stage and task:
Job created based on actions
Stages created based on shuffles or wide transformation
Task created based on partition 
 
 How Spark Job Executes (Step-by-Step):
Step 1: User Writes Code
df.filter(df.age > 25).groupBy("city").count().show()

Step 2: Driver Creates DAG:
Spark creates a DAG (Directed Acyclic Graph) of transformations
Optimizes execution plan

Step 3: DAG → Stages
DAG is split into stages
Each stage contains multiple tasks

Step 4: Tasks Creation
Each stage is divided into tasks
Each task works on one data partition

Step 5: Task Execution
Driver sends tasks to executors
Executors process data in parallel

Step 6: Result Returned:
Executors send results back to Driver
Driver displays output
 
Execution Example:
df.filter(df.age > 25).groupBy("city").count().show() 
Execution Flow:
filter() → Transformation
groupBy() → Transformation (causes shuffle)
count() → Transformation
show() → Action (triggers job)
Create DAG
Split into stages:
Stage 1 → filter
Stage 2 → groupBy (shuffle)
Create tasks per partition
Execute in parallel
Visual Flow:
User Code
  ↓
Driver Program
  ↓
DAG Creation
  ↓
Stages → Tasks
  ↓
Cluster Manager
  ↓
Executors (Worker Nodes)
  ↓
Result → Driver

Fault tolerance means the system can recover from failures without losing data or stopping the job.
Spark uses lineage graph (DAG):
If data lost → recompute using transformations
No need to store intermediate data

6. Exception Handling
In PySpark, exception handling is done using try-except in the driver, while executor-level errors must be handled inside transformations like map or filter.
Exception Handling in Driver(try and except block):
Try:
df = spark.read.csv("wrong_path.csv")
df.show()
except Exception as e:
print("Error:", e) 
Handles errors like:
File not found
Syntax errors
Connection issues

Exception Handling in Executors(can’t handle using try except block):
Handle inside transformation:
def safe_div(x):
Try:
return 10 / x
Except:
return None
rdd.map(safe_div).collect() 
Filter bad data before operation:
rdd.filter(lambda x: x != 0).map(lambda x: 10 / x).collect() 
Logging Errors:
import logging
logging.error("Something went wrong") 
Real-Life Analogy:
Driver = Manager
Executors = Workers
Manager can catch his own mistakes
But worker mistakes must be handled at worker level

A transformation is narrow: when Each output partition depends on only one input partition
Key Point:
No data movement between partitions

Fast

Wide Transformations:
A transformation is wide when: Output partition depends on multiple input partitions
Key Point:

12. What is meant by Data Skewness? How to deal with this?
Data Skewness
Data Skew occurs when data for certain keys is unevenly distributed, causing some Spark tasks to run much longer than others. It leads to poor parallelism and slow jobs. Common solutions include broadcast joins, salting heavy keys, and repartitioning using high-cardinality columns. 
Solutions:
Salting
Broadcast small table
Repartition by better column

25. Difference Repartition vs Coalesce
To control parallelism, performance, and number of output files.
Spark works on partitions. If partitions are not managed properly:
jobs become slow
resources are wasted
too many small files are created
More partitions → more parallelism
Fewer partitions → less overhead

repartition(n)
Increases or decreases number of partitions
Causes a full shuffle
Expensive
Used when you want balanced partitions
example: 
df = df.repartition(10)
 
When to use it :
Before large joins (Joins & groupBy need balanced data.)
Before writing large files
When existing partitions are unbalanced(Some partitions huge, some small → slow job. Repartition redistributes data evenly.)
Example:
Before:
Partition 1 → 100 rows 
Partition 2 → 5 rows 
Partition 3 → 200 rows 
After repartition(2):
Partition 1 → ~150 rows 
Partition 2 → ~155 rows 

Balanced,Expensive (shuffle)


coalesce(n)
Only reduces number of partitions
NO shuffle (faster)
Data is moved minimally
Example :
df = df.coalesce(2) 
When to use :
After filtering data(Data shrinks but partitions remain same → waste resources.  Fewer tasks, Better resource usage)
Before writing a small output
When you want fewer output files
By default: df.write.parquet("output/")
Creates many small files.
df.coalesce(1).write.parquet("output/")- Single output file
Example:
Before:
Partition 1 → 100 rows 
Partition 2 → 5 rows 
Partition 3 → 200 rows 
After coalesce(2):
Partition 1 → 100 rows 
Partition 2 → 205 rows   ❌ (imbalanced)
Fast,Uneven data distribution
 

We use repartition and coalesce to control the number of partitions in Spark, which helps improve parallelism, balance workload, reduce small files, and optimize performance. Repartition performs a full shuffle and is used when increasing or balancing partitions, while coalesce reduces partitions without shuffle and is used after filtering or before writing output.

Create a udf

from pyspark.sql.functions import udf
from pyspark.sql.types import StringType

def category_func(age):
    return "Senior" if age > 28 else "Junior"

udf_func = udf(category_func, StringType())

Register a udf:
spark.udf.register("my_udf_sql", category_func, StringType())

Why UDF is Slow?
UDFs are slow because they involve serialization between JVM and Python and bypass Spark’s Catalyst optimizer.

Spark runs in JVM
Python runs separately
Data moves between JVM ↔ Python (serialization)
Result -Slow performance, Breaks Spark optimization

30. Difference groupByKey vs reduceByKey
In PySpark, both reduceByKey() and groupByKey() are used on RDDs with (key, value) pairs,
reduceByKey is more efficient than groupByKey because it performs local aggregation before shuffle, reducing data transfer and improving performance.
groupByKey()
Groups all values for a key into a list
Input:
rdd = sc.parallelize([("a", 1),("a", 3),("b", 2),("b", 4)])
rdd.groupByKey().collect() 
Output:
('a', [1, 3])
('b', [2, 4])
 Problems:
No pre-aggregation no operation before shuffles
High data shuffle
High memory usage
Can cause OOM (Out Of Memory)
 
reduceByKey()
Aggregates values using a function
Input:
rdd = sc.parallelize([("a", 1),("a", 3),("b", 2),("b", 4)])
rdd.reduceByKey(lambda x, y: x + y).collect()
Output:
('a', 4)
('b', 6)
Benefits:
Reduces data before shuffle
Less network traffic
Better performance
 
When to Use What:
Use reduceByKey():
For aggregation ( x) ✅
Use groupByKey():
Only when you really need all values (rare case)
 
Why NOT just use normal operations?
Because data is distributed across partitions
Without these function You can’t combine data across machines
These functions: Bring related data together, Perform distributed aggregation

groupByKey → slow (shuffle heavy)
reduceByKey → efficient (combines before shuffle)

31. How to calculate no. of partitions
Number of Partitions
Number of partitions in PySpark is calculated based on data size and cluster cores, typically using 128–256 MB per partition or 2–4 times the number of CPU cores.
Suppose:
Data = 50GB
Cluster = 16 cores
Step1:
50GB / 128MB(HDFS block size (default ~128 MB)) ≈ 400 partitions
Step2:
16 × 4 cores = 64 partitions
Use ~200–400 partitions
Partitions = max( data_size / partition_size, 2–4 × total cores) 


How to Check Partitions:
df.rdd.getNumPartitions()

35.Star schema vs Snowflake schema:

Star schema has a central fact table connected to denormalized dimension tables for faster queries, while snowflake schema normalizes dimension tables into multiple related tables for better data consistency but with more complex joins.
 
What is Star Schema?
A Star Schema is a data modeling structure where one Fact table is directly connected to multiple Dimension tables.

Simple design

Disadvantages:

37. Types of plan created in pyspark

Types of Plans in PySpark:

Unresolved Logical Plan:
This plan is "unresolved" because Spark does not yet know if the column names or table names you used actually exist, or what their data types are. 
It only checks if the query is syntactically correct.

Analyzed Logical Plan :
Spark takes the Unresolved Logical Plan and consults the Catalog 
What happens:
It verifies that the table actually exists.
It checks if the column is present.
It assigns data types (e.g., Integer, String) to the columns. 
If a column or table name is misspelled, the process fails here with an AnalysisException.

 
Optimized Logical Plan:
This is created using Catalyst Optimizer
 It optimizes the query without changing the final output
What happens:
Spark improves the plan for better performance
Use below strategies:
Predicate Pushdown: Moving filters (.filter() or .where()) as close to the data source as possible so Spark reads less data from disk.
Projection Pruning: Selecting only the columns actually needed for the final output, ignoring the rest.
Constant Folding: Evaluating constant expressions at compile-time (e.g., converting 1 + 1 directly to 2).
Reordering operations

Example:
Apply filter before select if beneficial
Remove unused columns
 
Physical Plan:
Physical Plan turns Optimized Logical Plan into executable code (Low-level RDD operations).
What happens:
Spark generates multiple physical plans and evaluates them using a Cost-Based Model (CBO) (estimating CPU, memory, and I/O costs).
Chooses strategies like:
Hash Join
Sort Merge Join
Broadcast Join
chosen plan is selected as the Selected Physical Plan, which is then broken down into DAG stages and tasks for cluster execution.

41. What is Z-Ordering?
Z-Ordering is a data optimization technique used in Delta Lake (with PySpark) to physically reorder data based on one or more columns so that related data is stored closer together.
 
Before Z-Ordering, data is randomly distributed across files, so Spark scans all files during filtering. After applying Z-Ordering, related data is clustered together, allowing Spark to skip irrelevant files and significantly reduce scan time.
 
Why Do We Need It?
Even after partitioning:
Data inside files is still random ❌
Queries scan unnecessary data ❌
 
How to Implement (PySpark / SQL):
spark.sql("""
OPTIMIZE sales_table
ZORDER BY (city, user_id)
""")

 56. Types of OOM (Out Of Memory) in Spark:
Driver Out Of Memory: (Driver node memory gets exhausted)
Common Causes
Using collect() on huge data
Large broadcast variables
Too much metadata/logging
Very large result set returned to driver
Solution
Avoid collect() on large data
Use show() or limit()
Increase driver memory
Write output to storage instead
 
Executor Out Of Memory: (Executor memory becomes insufficient during task execution.)
Common Causes
Large shuffle operations
Data skew
Huge joins/groupBy
Large partitions
Caching excessive data
Solution
Repartition data properly
Increase executor memory
Optimize joins
Use broadcast joins
Reduce shuffle
   
Shuffle OOM: (OOM during shuffle stage)
 Usually occurs in:
joins
groupBy
orderBy
Distinct
Causes
Large shuffle partitions
Data skew
Insufficient memory
Solution
Tune shuffle partitions
Use salting for skew
Optimize joins
Increase memory

Cache/Persist OOM: (Cached DataFrames consume excessive memory)
 Causes
Caching huge datasets unnecessarily
Multiple cached DataFrames
Solution
Use unpersist()
Cache only reused datasets
Use MEMORY_AND_DISK strategy

59. In between bucketby and partitionby which is having higher Cardinality?
Partitioning is preferred for low cardinality columns because it creates separate directories. Bucketing is better for high cardinality columns because it distributes data into fixed buckets using hashing and avoids creating too many small partitions.
